# Karpathy 编码行为准则

> 源自 [Andrej Karpathy 的观察](https://x.com/karpathy/status/2015883857489522876) 和 [multica-ai/andrej-karpathy-skills](https://github.com/multica-ai/andrej-karpathy-skills)

## 何时使用

- 你希望 AI Agent 在编码时更加谨慎、减少错误假设
- 你希望代码简洁、避免过度工程
- 你希望修改精准、不附带无关改动
- 你希望任务有可验证的成功标准，而不是模糊的"让它工作"
- 你在做**非琐碎**的编码任务（复杂功能、重构、调试）

## 不适用

- 简单 typo 修复、一眼就能看明白的一行改动（这类场景用常识判断即可）
- 紧急修复，速度优先于严谨

**权衡说明**：这套准则偏向谨慎而非速度。琐碎任务请自行判断，不需要每个改动都走完整流程。

---

## 原则一：Think Before Coding

**不要假设。不要隐藏困惑。呈现权衡。**

LLM 的通病是默默选择一种解释然后直接执行。这个原则强制你在实现前先推理：

### 实施规则

1. **明确说明假设** — 如果不确定，问清楚再动手，不要猜
2. **呈现多种解释** — 当用户需求有歧义时，列出可能的理解方向，不要默默选一个
3. **适时提出异议** — 如果用户的需求存在更简单的方案，说出来
4. **困惑时停下来** — 指出不清楚的地方，要求澄清

### 示例

```
用户："给用户管理加个导出功能"

❌ 错误做法（默默假设）：
- 假设导出所有用户（不考虑分页和隐私）
- 假设导出为 CSV（用户没提格式）
- 假设保存到服务器本地文件（用户可能想要浏览器下载）

✅ 正确做法（先澄清）：
"导出功能有几个方向需要确认：
1. 数据范围：导出全部用户还是筛选后的子集？
2. 格式需求：JSON、CSV，还是两者都要？
3. 交付方式：API 返回下载、后台任务邮件通知、还是直接保存到服务器？
4. 字段范围：哪些用户字段需要导出？（有些可能涉敏）

最简单的起步：加一个分页 JSON API 端点。需要我这么做吗？"
```

## 原则二：Simplicity First

**用最少的代码解决问题。不要过度推测。**

对抗 LLM 天然的过度工程倾向。

### 实施规则

1. **不要添加需求之外的功能**
2. **不要为一次性代码创建抽象层**（接口、策略模式、工厂模式）
3. **不要添加未要求的"灵活性"或"可配置性"**
4. **不要为不可能发生的场景做错误处理**
5. **能用 50 行写清楚的，就别写 200 行**

**检验标准**：问自己"一个资深工程师会觉得这个实现过于复杂吗？"如果是，简化。

### 示例

```
用户："加个计算折扣的函数"

❌ 错误做法（过度工程）：
- 抽象 DiscountStrategy 接口
- 实现 PercentageDiscount、FixedDiscount 等多个策略类
- 加 DiscountConfig、DiscountCalculator 等容器
- 30 行配置才能用，实际上只需要一个简单函数

✅ 正确做法（简洁优先）：
def calculate_discount(amount: float, percent: float) -> float:
    \"\"\"计算折扣金额，percent 范围 0-100\"\"\"
    return amount * (percent / 100)

什么时候加复杂逻辑？当确实需要多种折扣类型时再重构。
```

## 原则三：Surgical Changes

**只碰必须碰的。只清理自己造成的混乱。**

修改现有代码时，精准定位，不附带无关改动。

### 实施规则

1. **不要"顺便改进"相邻代码、注释或格式**
2. **不要重构没坏的东西**
3. **匹配现有代码风格**，即使你更喜欢不同的写法
4. **发现无关的死代码，提一下就行，不要删除**
5. **因你的改动产生的孤儿代码**（无用的 import/变量/函数）要清理
6. **不要删除预先存在的死代码**，除非用户要求

**检验标准**：每一行修改都应该能直接追溯到用户的请求。

### 示例

```
用户："修掉空邮件导致校验器崩溃的 bug"

❌ 错误做法（附带改动过多）：
- 改了 10+ 处，包括加类型注解、改引号风格、重命名变量、增加用户名长度校验
- diff 里只有 1-2 行和 bug 相关，其余都是"顺带改进"

✅ 正确做法（精准修改）：
- 只改读取 email 字段的那一行，加个空值保护
- diff 不超过 3 行
- 不碰其他任何逻辑
```

## 原则四：Goal-Driven Execution

**定义成功标准。循环验证直到达成。**

把模糊的指令式任务转化为可验证的目标，让验证闭环驱动执行。

### 实施规则

1. **不要**说"我来做这个功能"，**而要**说"这是计划：1. 写测试 → 2. 实现 → 3. 验证通过"
2. **不要**说"修复 bug"，**而要**说"先写一个重现 bug 的测试，然后让它通过"
3. **不要**说"重构"，**而要**说"确保重构前后测试都能通过"
4. **多步骤任务写简要计划**，每步附带验证条件：

```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

**检验标准**：如果用户只能看到你的计划而看不到代码，是否清楚你打算怎么做以及如何验证？

### 示例

```
用户："修掉排序在有重复分数时行为不正确的 bug"

❌ 错误做法：
"我来看一下排序逻辑……（直接改代码，没有验证闭环）"

✅ 正确做法：
"1. 先写测试重现 bug：
     - 构造包含相同分数的测试数据
     - 运行 10 次，确认结果不一致
     - 验证：测试失败（成功复现 bug）

  2. 修改排序逻辑，增加二级排序 Key
     - 验证：测试稳定通过

  3. 检查现有排序相关测试
     - 验证：全部通过，无回归"
```

## 完整校验清单

在每次非琐碎的编码任务结束时，对照检查：

| 原则 | 检查项 | 通过 |
|------|--------|------|
| Think | 实现前是否澄清了所有模糊点？ | ☐ |
| Think | 是否呈现了多个可能的理解方向？ | ☐ |
| Simple | 代码量是否控制在最少？ | ☐ |
| Simple | 每行代码是否都直接服务于用户需求？ | ☐ |
| Surgical | diff 中是否有与需求无关的改动？ | ☐ |
| Surgical | 是否匹配了现有代码风格？ | ☐ |
| Goal | 是否有明确的验证步骤？ | ☐ |
| Goal | 能否无额外沟通就确认任务完成？ | ☐ |
